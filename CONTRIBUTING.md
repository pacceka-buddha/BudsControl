# Contributing to Buds Control

There are three ways to contribute. Hardware reports help the most right now.

## 1. Hardware reports

What has been tried so far: Windows 10/11 with **OnePlus Buds 4**; Linux on Ubuntu 24.04 with GNOME (X11 and Wayland)
and Buds 4, see [docs/LINUX.md](docs/LINUX.md); macOS 27 on one Apple silicon Mac with **OnePlus Buds 3**. Intel Macs,
other Linux distributions and desktops, and every other earbud model are untested. If you try Buds Control on any of
them, open a **Hardware report** issue and say what worked and what didn't. Useful details:

- OS and version (and on Linux: distribution, desktop, X11 or Wayland).
- Earbud model, and the output of `budsctl status`, `budsctl devices` and `budsctl sdp`.
- The log file (paths are in the [README](README.md#troubleshooting)).

The log and `budsctl devices` contain Bluetooth device names and addresses. Replace them with placeholders before
posting if you'd rather keep them private.

## 2. Bug reports and ideas

Use the issue templates. For a bug, include the steps to reproduce, what you expected and what happened, and the
details listed above.

## 3. Pull requests

1. Fork the repository and create a branch from `main`.
2. Set up the project as described in [Building from source](README.md#building-from-source) (Node 20.19+ or 22.12+).
   Most work can be done without earbuds: `BUDS_FAKE=1 npm run tauri dev` runs the app against simulated buds.
3. Keep the change focused, and add or update tests where it makes sense (`crates/buds-core/tests`,
   `src/lib/*.test.ts`).
4. Run the checks before pushing:

   ```bash
   cargo fmt --all --check
   cargo clippy --workspace --all-targets -- -D warnings
   cargo test --workspace
   npm run check
   npm test
   ```

5. If you changed a Rust type that is exported to TypeScript, commit the regenerated files in `src/lib/bindings/`
   (`cargo test` writes them; CI fails if they are out of date).
6. Open the pull request and describe what changed and how you tested it (with which OS and earbuds, if any).

### Where things live

- Protocol facts: [docs/PROTOCOL.md](docs/PROTOCOL.md). The command table and parsers are in `crates/buds-core`.
- New earbud models come from the device catalog, `crates/buds-core/src/catalog/generated.rs`, which is generated by
  `tools/convert_catalog.py`; don't edit it by hand.
- The crate layout is in the [README](README.md). Manual hardware checklist: [docs/TESTING.md](docs/TESTING.md).
  Linux specifics: [docs/LINUX.md](docs/LINUX.md).

### Raw commands

The developer tools can send arbitrary commands to the earbuds. Commands outside the read-only `0x01xx` range can
change settings on the buds; don't ask other people to send them without explaining what they do.

## Code of conduct

Be kind and assume good faith. Harassment or personal attacks are not tolerated; maintainers may remove comments and
block accounts that cross that line.
